MC 的 16 色染色前缀目前被 `block_families.py` 按「材质类型」吞掉：`lime_wool` 和
`green_wool` 都命中 `("wool","fabric")`，`pink_terracotta` 命中 `("terracotta","brick")`。

## 0. 结论摘要

**1. 实现方式：全部 21 个变体都用「离线烘焙变体贴图」，包括 wool 和 concrete。**

这条**推翻了任务书 (a)/(b) 的分工**。任务书的直觉是对的（wool/concrete 在 MC 里确实是
「中性底 × 染料」），但把 tint 放在**运行时**在**本项目**里代价过高：

- 变体的命名契约本来就是 `<family>_<colour>` → `T_MC_fabric_lime`。**每个变体都要一张
  独立贴图**，这笔开销无论如何都要付，运行时 tint 省不掉它；
- `tools/import_family_materials.py` 开头写明材质图被**冻结**为已证可用的形状
  （`TextureSampleParameter2D → BaseColor`、`Tiling × TexCoord → Coordinates`、
  `Constant → Roughness`），并明确禁止加节点。任务书提议的 `Tint` 向量参数**不在**该形状内；
- 更关键：ART-S5 期间已实测过 `Tint` 向量参数——「实例上设对了、也连对了，**改动了 0 个像素**」。
  一个曾经在本项目里完全失效的节点，不该被用在 P1 缺陷修复的关键路径上；
- 离线烘焙的精度是**实测 dE2000 = 0.00**（不是"够用"，是精确命中），而且可以在 **UE 启动前**
  用 PNG 级断言验证。运行时 tint 只能在引擎内验证，而"引擎内验证"正是上次骗过我们的那一环。

成本：21 张 512×512 PNG ≈ 9 MB，走的是既有的 per-family tiling 材质系统，**不新增 shader 变体**。

**2. Q1「brick 乘法到不了 pink/cyan」——不成立，但结论（用离线贴图）仍然对，理由不同。**

乘法**能**命中颜色，前提是 tint 用**预制增益** `目标/底色` 而不是**染料色**：

| brick 底色 (132,94,82) | 结果 | 对 MC 目标 dE2000 |
|---|---|---|
| × 染料 pink(243,139,170)/255 | (126, 51, 55) | **9.6** |
| × 增益 (1.212,0.819,0.951) | (160, 77, 78) | **0.00** |
| × 染料 cyan(22,156,156)/255 | (11, 58, 50) | **19.4** |
| × 增益 (0.659,0.979,1.122) | (87, 92, 92) | **0.00** |

所以"乘法做不到"只在**把染料色当 tint** 时成立。**用离线贴图的真正理由是「纹理图案」，不是颜色**：
砖墙的砂浆缝会完整保留（纹理标准差 15.4），而 MC 陶土是光滑的黏土（烘焙后 2.6）。
见 §2.1 的视觉证据。

**3. Q3「运动场要不要让 lime 退成绿」——问题前提不成立，不要改几何。**

保存档的运动场**不是**一块单色场地。实测（见 §2.3）是：

```
        ┌──────────────── 13 行 pink_terracotta（跑道）────────────────┐
        │  ┌────────── 球场：lime_wool / green_wool  8 格交替条纹 ──────┐ │
        │  │  这是割草机条纹（mowing pattern），不是随机配色           │ │
        │  │  white_wool = 边线/中圈/禁区线                            │ │
        │  └──────────────────────────────────────────────────────────┘ │
        └──────────────────────────────────────────────────────────────┘
```

`lime_wool` 是**一半的条纹**。把它压向绿会直接抹掉割草条纹
（`lime_wool` 与 `green_wool` 的 dE2000 = 25.8；压平后该分离度归零）。
**结论：`fabric_lime` 必须是 MC 真正的亮黄绿 (112,185,25)，`fabric_green` 是 (84,109,27)，
几何完全不用改**——保存档已经把正确的图案摆好了，我们只需要把两个颜色配对。

**4. 不需要新增家族。** 陶土走 `brick_<颜色>`，羊毛走 `fabric_<颜色>`，混凝土走
`concrete_<颜色>`。不碰 `FAMILIES` 元组就没有索引位移风险。`clay` 方块在存档里 **0 块**，
不需要 `clay` 族。

**5. 任务书的 19 个变体里有 1 个是误报，且漏了 3 个大的（其中 1 个占全混凝土的 77%）。**
详见 §1.2。

### 1.3 一个我修不了、但必须记录的既有缺陷

`fabric` 族同时收 **stained_glass / stained_glass_pane**（红 198、白 500、黑 417、橙 68、
浅灰 10 ≈ 1,200 块）。我们的材质是**不透明**的，所以染色玻璃现在渲染成不透明的近白块。
给它上颜色变体能让它变成「不透明的彩色块」——比白色好，但**仍然不是半透明玻璃**。
真要修需要透明/遮罩材质，属另一件事。本文件只保证颜色正确。

### 1.4 我做了什么颜色校正，为什么

**用「实机外观色」而非「地图基色」。** MC 方块有两套公开数值，用途不同：

- **地图基色**（`Map_item_format` / wiki 的 `#FFFFFF`）——地图物品上那个像素的颜色；
- **实机外观色**——玩家在游戏里看到的方块颜色。

我全部采用**实机外观色**，因为目标是「用户看到什么」。两者差距不小：

| 颜色 | 地图基色 | 实机外观 | 差 |
|---|---|---|---|
| white_concrete | `#FFFFFF` (255,255,255) | (207,213,214) | 亮 48/通道 |
| yellow_concrete | `#E5E533` (229,229,51) | (241,175,21) | 色相不同 |
| lime_concrete | `#7FCC19` (127,204,25) | ( 94,169,25) | 暗 33 |

若用 `#FFFFFF` 做白混凝土，增益会是 (2.28,2.28,2.32)，且会**削顶**（255 之上截断），
把混凝土压成一张纯白死板。用 (207,213,214) 才有灰阶层次。

**羊毛修正量本身也是一个判断点。** 染料表里 `lime_dye = (128,199,31)`，但
`lime_wool` 实机是 **(112,185,25)**——因为羊毛贴图本身不是纯白（约 0.88）。
如果直接拿染料色当目标，场地上所有条纹会整体偏亮偏饱和。任务书 §2 给的就是染料值，
我换成了羊毛值。

## 2. 三个具体问题的答案

### 2.1 Q1 — brick 乘法能不能达到 pink/cyan？

**分两问答，因为答案相反：**

**颜色：能。** 但必须是**预制增益**不是**染料色**（§0 表格）。原因很直接：目标是
(160,77,78)，底色 (132,94,82)，R 通道**需要变亮**（增益 1.212 > 1）。而染料 pink
是 (243,139,170) → 乘出来 (126,51,55)，**变暗了**，dE 9.6。cyan 更糟：染料 (22,156,156)
→ (11,58,50)，dE 19.4。**把染料色当 tint，等价于假设底色是纯白**——brick 底色不是。

**图案：不能，这才是问题所在。** 这是视觉判断，我实际渲染出来看了：

| 做法 | 对目标色 dE | 纹理标准差（图案保留度） | 观感 |
|---|---|---|---|
| 不处理（brick 原样） | — | 15.7 | 砖墙 |
| 乘增益 | **0.00** | 15.4 | **粉色砖墙**——砂浆缝清晰可见 |
| 高斯模糊 4px + 乘增益 | 0.00 | 5.0 | 接近黏土，仍有残留 |
| **高斯模糊 12px + 乘增益** | 0.00 | **2.6** | **光滑陶土** ✅ |
| 去饱和后重着色 | 0.24 | 2.2 | 光滑，但偏"糊"，损失高光 |

**推荐公式（具体）：**

```python
# 1) 先去图案：对 512×512 的 brick.png 做高斯模糊，半径 12 px
base = Image.open("out/families/brick.png").convert("RGB")
base = base.filter(ImageFilter.GaussianBlur(12))        # tex_std 15.7 -> 2.6

# 2) 再乘增益（sRGB 逐通道 LUT），增益 = 目标实机色 / 模糊后底色均值
#    模糊后底色均值实测 (131.7, 93.8, 81.9)
for colour, gain in GAINS.items():
    out = base.point([... 3×256 LUT ...])               # 见 §4
    out.save("out/families/brick_%s.png" % colour)

# GAINS (sRGB, 逐通道) —— 实测 gain × 底色 = 目标，dE 0.00
#   brick_pink  (1.215, 0.821, 0.953)  -> (160, 77, 78)   MC pink_terracotta
#   brick_cyan  (0.661, 0.981, 1.124)  -> ( 87, 92, 92)   MC cyan_terracotta
#   brick_green (0.577, 0.874, 0.513)  -> ( 76, 82, 42)   MC green_terracotta
```

**为什么模糊 12px 合适**：砂浆缝在 512 贴图上约 3–6 px 宽，12 px 半径把它抹掉，
同时保留砖块之间大尺度的明暗起伏（标准差剩 2.6 而不是 0）——
这正是黏土的观感：**均匀但有微妙色斑**。模糊到 0 会变成塑料。

**不要**用「去饱和再上色」那条路：dE 略高（0.24）且把砖面的高光变化一起抹平，
看起来像纯色卡而不是材质。

### 2.2 Q2 — fabric × 染料，能得到 MC 的 lime_wool 观感吗？

**不能。我实际算了。** 三行对比（目标是 MC lime_wool 实机色 (112,185,25)）：

| 做法 | 结果 RGB | 对 MC dE2000 | 判定 |
|---|---|---|---|
| 朴素 sRGB 乘 `fabric × lime(128,199,31)/255` | ( 89,141, 22) | **13.8** | ❌ 明显偏暗、偏脏 |
| UE 实际做的（贴图解到线性再乘） | ( 87,140, 19) | **14.1** | ❌ 同上 |
| 预制增益 (0.629,1.027,0.136) | (112,185, 25) | **0.00** | ✅ 精确 |

**全部 9 个 fabric 变体的朴素乘法误差：**

| 变体 | 朴素 sRGB 乘 | dE | 预制增益结果 | dE |
|---|---|---|---|---|
| `fabric_black` | ( 20, 20, 24) | 0.6 | ( 20, 21, 25) | 0.00 |
| `fabric_blue` | ( 42, 48,123) | 5.7 | ( 53, 57,157) | 0.00 |
| `fabric_brown` | ( 91, 59, 36) | 5.9 | (114, 71, 40) | 0.00 |
| `fabric_green` | ( 66, 88, 16) | 7.4 | ( 84,109, 27) | 0.00 |
| `fabric_red` | (123, 32, 27) | 7.8 | (161, 39, 34) | 0.00 |
| **`fabric_lime`** | ( 89,141, 22) | **13.8** | (112,185, 25) | 0.00 |
| `fabric_yellow` | (177,153, 44) | **15.4** | (248,198, 39) | 0.00 |
| `fabric_orange` | (174, 90, 21) | **15.5** | (240,118, 19) | 0.00 |
| **`fabric_light_blue`** | ( 40,126,157) | **16.2** | ( 58,175,217) | 0.00 |

**规律（这解释了为什么朴素 tint 系统性失败）**：两个 0–1 之间的数相乘，
结果**永远比两者都小**。fabric 底色是白的 0.70 倍（178/255），所以朴素乘法的结果
**不可能超过 0.70 × 目标**。目标越亮，错得越狠——所以最亮的
`light_blue`(16.2)、`orange`(15.5)、`yellow`(15.4)、`lime`(13.8) 误差最大，
而 `black`(0.6) 反而几乎正确（因为黑色本来就暗，乘两次正好）。

要让结果**变亮**，增益必须 **> 1**——即必须**除以底色**。这就是预制增益在做的事，
也是它能把 dE 压到 0.00 的原因。

> **对本项目尤其要紧**：`fabric_lime` 和 `fabric_light_blue` 恰好是朴素乘法最不准的两个，
> 而 `fabric_lime` 正是**球场条纹**。按朴素 tint 做，球场会是暗橄榄色，
> 割草条纹的对比度也一起塌掉。

### 2.3 Q3 — 运动场应该怎么配色（我的独立判断）

**先纠正问题前提。** 任务书问「是否该让场地用 `green_wool`、lime 只做边线」。
我把存档里运动场区域的体素**渲染成平面图看了**，实际结构是：

```
  粉陶土跑道（pink_terracotta，俯视 13 行环带）
  └─ 内部球场：lime_wool 与 green_wool 各 8 格宽、交替排列
     = 割草机条纹，横贯整个场地（不是边线）
     white_wool = 中圈 / 禁区线 / 边线
```

**实测证据**（在第 5 层平面沿一条横线取样，单位＝格）：

```
WW..WW..WW..WW..WW..WW..WW.GGLLWLLLLLGGGGGGGGLLLLLLLLGGGGGGGGLLLLLLLLGGGGGGGG
LLLLLLLLGGGGGGGGLLLLLLLLGGGGGGGGLLLLLLLLGGGGGGGGLLLLLLLLGGGGGGGG...W..W..W
       └──────── 8 格 G ─┘└─ 8 格 L ─┘└─ 8 格 G ─┘  ← 规律交替
```

`lime` 平均条宽 8.0 格、`green` 平均条宽 8.0 格、`white` 平均宽 1.4 格。
**所以 lime 是场地的一半，不是边线。**

**我的建议（按重要性排序）：**

1. **不改几何。** 存档已经把割草条纹摆好了，这是它的设计。我们只需要
   `fabric_lime` 和 `fabric_green` 两个颜色**配对**，条纹自动出现。
   这是**零几何改动**的解法，优先级最高。
2. **`fabric_lime` 保持 MC 真值 (112,185,25)，不要压向绿。**
   任务书担心「亮黄绿做一大片场地是否合适」——它不合适**做单色场地**，
   但它不是单色场地，它是**条纹的一半**。真实球场就是深浅相间的割草纹。
   dE(`lime_wool`,`green_wool`) = **25.8**；如果按任务书把 lime 压成绿，
   这个分离度归零，**球场会变成一块没有图案的平板**。
3. **`brick_pink` 用 MC 的暗玫瑰土色 (160,77,78)。** 提醒：MC 的「粉陶土」
   **不是泡泡糖粉**，是偏暗的玫瑰土红。跑道看起来会是**哑光的砖粉色**，
   和真实的塑胶跑道接近。如果按「粉」字面理解去调亮，就会偏。
4. **`white_wool` 必须给足亮度 (233,236,236)。** 球场线是白色，如果 fabric 底色
   停在 (178,180,184)，边线会比场地还灰，图案读不出来。

**关于我 S5 里那个 `sports` 族——我错了，而且它帮不上忙。**
我在 ART-S5 给 `sports` 烤了一张**单色**绿 (96,122,74)。实测它**在存档里 0 块**

## 3. 需要新增家族吗？

**不需要。**

| 候选 | 判断 | 理由 |
|---|---|---|
| `clay`（黏土族） | **不要** | 存档里 `clay` 方块 **0 块**。染色陶土走 `brick_<颜色>` 已足够 |
| `terracotta`（陶土族） | **不要** | 与 `brick` 变体功能重复。新增族要动 `FAMILIES`，虽然只允许追加是安全的，但**没必要承担这个风险** |
| `ice`（冰族） | **不要**（记录在案） | `blue_ice` 只有 178 块，且现在落到近白 `fabric`。不值得为 178 块开一个族；已在 §1.2 单独标注 |
| `glass`（玻璃族） | **不建议现在做** | 染色玻璃/玻璃板约 1,200 块，且难点是**透明**不是颜色。属另一个议题（§1.3） |

**变体一律用 `<现有族>_<颜色>` 命名**：`brick_pink` / `fabric_lime` / `concrete_green`。
好处：`FAMILIES` 元组一个字符都不用改，**零索引位移风险**。

> 注意：变体**不需要**和「源贴图」同名匹配。`brick_pink` 用的是 brick 贴图模糊后的版本，
> 但名称只影响它去取 `T_MC_brick_pink` 这张**独立贴图**。命名是契约，不是继承关系。

## 4. 落地约束（给工程师）

### 4.1 命名与解析链

| 层 | 名称 | 说明 |
|---|---|---|
| PNG | `out/families/<family>_<colour>.png` | 512×512 POT |
| UE 贴图 | `T_MC_<family>_<colour>` | **Wrap** 寻址（关键，见 4.3） |
| UE 母材质 | `M_MC_<name>` | 按名解析的第一顺位 |
| UE 材质实例 | `MI_MC_<name>` | 第二顺位 |
| OBJ | `usemtl <family>_<colour>` | 例 `usemtl fabric_lime`、`usemtl brick_pink` |

变体名 = `<family>_<colour>`，无颜色时保持现状（`usemtl fabric`）。

### 4.2 `block_families.py` 的映射规则（规格，不是实现）

变体匹配**必须排在现有通用规则之前**，否则 `lime_wool` 会先命中 `("wool","fabric")`。

```
DYE     = white|orange|magenta|light_blue|yellow|lime|pink|gray|light_gray
          |cyan|purple|blue|brown|green|red|black
TOKEN   = wool|carpet|bed|banner|stained_glass|stained_glass_pane|concrete|terracotta
EXCLUDE = nether_brick | _concrete_powder | glazed | blue_ice
```

1. 用 `^(DYE)_(.+)$` 匹配方块名，取 `colour` 与 `bare`。
2. `bare` 去掉 `_wall/_slab/_stairs` 后缀后，落在 `TOKEN` 里才算变体。
3. `EXCLUDE` 命中则**跳出**，回落到现有规则。

逐条验证（这些是实际会遇到的）：

| 方块 | 期望 | 规则结果 |
|---|---|---|
| `lime_wool` | `fabric_lime` | ✅ bare=`wool` ∈ TOKEN |
| `pink_terracotta` | `brick_pink` | ✅ |
| `white_concrete` | `concrete_white` | ✅ |
| `white_concrete_powder` | 回落（→ gravel） | ✅ EXCLUDE `_concrete_powder`（粉末是另一种方块） |
| `red_nether_brick_wall` | 回落（→ brick，**原样**） | ✅ EXCLUDE `nether_brick` |
| `lime_glazed_terracotta` | 回落（→ brick，**原样**） | ✅ EXCLUDE `glazed`（有图案的釉陶，32 块，不值得做） |
| `blue_ice` | 回落（→ fabric） | ✅ EXCLUDE `blue_ice`（178 块，另案） |
| `red_tulip` | 回落（→ leaves） | ✅ bare=`tulip` ∉ TOKEN |
| `white_wall_banner` | 回落（→ plaster） | ✅ bare=`wall_banner` ∉ TOKEN |
| `brown_mushroom_block` | 回落（→ bark） | ✅ bare=`mushroom_block` ∉ TOKEN |

目标色表建议直接放在 `block_families.py` 旁边的一个 `VARIANT_TARGET` 常量，
让烘焙脚本和映射脚本**读同一份**，避免两处漂移（这正是 `rolemap` / `block_families`
当初合并成单一真相源的理由）。

### 4.3 三个已知会静默失败的点

1. **WRAP 寻址**。`import_family_materials.py` 已把这点写成第 1 号约束：per-family
   贴图用 block 单位 UV，任何超过 1 格的四边形都会越界，`Clamp` 会把边缘纹素拉满整个面。
   变体贴图**同样必须 Wrap**。
2. **烘焙顺序**。`gain` 必须作用在**缩放之后**。LANCZOS 重采样会混合邻域，
   先烘焙再缩放会让结果依赖滤波器，§1.1 的 gain 就不再命中。
3. **`brick_<颜色>` 的源必须是模糊后的贴图**，且**四个陶土变体共用同一张模糊底**。
   否则四个变体的纹理标准差会不一致，同一面墙的陶土看起来会"不同材质"。

### 4.4 烘焙实现（与 ART-S5 的 LUT 方式一致）

```python
GAIN = {  # sRGB 逐通道，实测 gain × 底色 = 目标，dE 0.00
  "brick_pink":       (1.215, 0.821, 0.953),
  "brick_cyan":       (0.661, 0.981, 1.124),
  "brick_green":      (0.577, 0.874, 0.513),
  "fabric_lime":      (0.629, 1.027, 0.136),
  # ... 其余见 §1.1
}
im = im.point([min(255, int(v * r)) for v in range(256)] +
              [min(255, int(v * g)) for v in range(256)] +
              [min(255, int(v * b)) for v in range(256)])
```

纯查表、构建期一次、运行期零成本，且**不可能像 `Tint` 那样静默失效**——
因为它改的是 PNG 字节，不是引擎状态。每个变体的实测 gain 已写入
`out/_art_table.md`（临时文件，见 §6）。

### 4.5 验证（PNG 级，UE 启动前）

在 UE 打开之前对 21 张变体贴图断言（这是唯一能挡住「参数设对了但没生效」的层级）：

| 断言 | 阈值 |
|---|---|
| 每张变体的通道均值 vs §1.1 目标 | **≤ 3**（实测可达 0） |
| `fabric_lime` / `fabric_green` 的 **dE2000 分离度** | **≥ 20**（MC 真值 25.8；低于 20 说明条纹会消失） |
| `fabric_*` 的 `G` 是否 `≥ R`（限于 green/lime 两个） | 必须成立 |
| `brick_*` 的纹理标准差 | **≤ 4**（>8 说明模糊没跑，砂浆缝还在） |
| `brick_*` 的 `R > G > B` 是否被破坏（pink/green/cyan 应当破坏，red 应当保持） | 逐项对照 §1.1 |
| `concrete_white` 的均值 | 必须 **≥ 200**（当前 112，这是最容易漏的一项） |

**再加一条整体断言**：运动场区域的两族交替条纹在渲染帧里必须仍可分辨——
即 Step「帧级 A/B」之外，单独裁球场区域比对 `fabric_lime` 与 `fabric_green`
的像素占比是否都在 30% 以上。若某一族占比掉到 0，说明映射把两个颜色合并了。

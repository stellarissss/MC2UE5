## 六、额外风险

- **陈旧 `.uasset`**：磁盘 PNG 是新的、编辑器里纹理是旧的。
  这是"我改了但没反应"的最可能成因，且**所有日志都是绿的**。
- **UV v-flip**：某个族静默显示另一个族的纹理，画面看着合理、无报错。
  → 继续 import `plan_layout()`。文档里 21 个 UV rect 全部列出。
  注意 **v 向上、row 0 是图像底部**，且 v 区间不对称
  （row 0 是 0.66927–0.99740 而非 0.66666–1.0，因为有 4 texel padding），
  **不要"整理"它们**。

图集布局参数（不要改）：4096×1536、8 列 × 3 行、pitch 512、**tile 504**、**pad 4**。
504+2×4=512 保持 2 的幂（mip 安全），504 是 8 的倍数（不浪费 BC1 边缘块）。

> **勘误（工程侧实测，2026-10-06）—— 已发布图集实为 4096×2048，不是 1536。**
> `plan_layout()` 把行数向上取整到 2 的幂：21 个族需要 3 行 → `rows = 4` → 高 2048。
> 因此：
> - 真实高度 **2048**，行数 **4**，第 3 行（r3）整行未使用；
> - 本文件与 `s5_material_spec.md` §4 列的 UV 表按 1536 高度算出，**v 值整体偏移**，
>   不可直接引用；`quartz` 实际是 `uv = [0.12598..0.24902] × [0.25195..0.49805]`，
>   不是文档里的 `[0.00260..0.33073]`；
> - 但**网格本身没问题**：`extract_structures.py` 与所有已生成 OBJ 都是 `import plan_layout()`
> 得到的，v 最大 0.99805，与 2048 一致。错的只有文档里的手抄数字。
> **结论不变：继续 `import plan_layout()`，永远不要手抄 UV。** 这次手抄直接产生了错误数字。
>
> **第二处勘误：汇总基线 "+27.0" 的算法。** 该值是**图像底部 1536 行**的均值，
> 它把 r2c5–c7 三格空格当成 (0,0,0) 一起平均了，偏乐观。
> 按 22 个已占用格平均，真实的烘焙前基线是 **(109.6, 106.2, 92.8)，R−B = +16.8**。
> 低于 +27.0，但对「读作沙子」的诊断没有影响——逐格的 60+ 才是问题所在。

## 10.2 两条我必须公开纠正的错误

**① `sha256(frame_A) != sha256(frame_B)` 这条验收标准是无效的 —— 这是我定的。**
QA 实测：**同一份输入连拍两帧，哈希不同**（max Δ31，479 px >8，0 px >32）。
渲染器不是逐字节可复现的，所以这个不等式**恒为真**，
**无论图集有没有变都会报绿**。而且实测 baked-vs-prebake 是
max Δ40 / 474 px >8，噪声底是 max Δ31 / 479 px >8 —— **两者不可区分**。
（那 2 个 >32 的离群点是 (539,375) 处一个 2×1 的 AA 抖动块，在道具边缘上。）

**正确做法**：先拍两帧**同一图集**建立噪声底，再用**逐像素阈值**比较
处理组与基线，而不是比哈希。**哈希判据就此作废。**

**② "Shipping 静默失败 = 删每目标中间件" —— 这条经验是错的，我传错了。**
QA 删了该目录**没有解决**。真实原因是 **UBA**：`link.exe` 在 UBA executor 下
退出 1，而**同一条命令单独执行退出 0**；`Q:/UBA` 对当前用户 ACL 上锁。
加 `-NoUBA` 后 link 通过，失败点移到 `WriteMetadata`，它单独执行同样退出 0。
**每一步都只在 UBA 下失败。**
